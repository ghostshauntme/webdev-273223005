## Что происходит при ошибках (fail)

- Некорректный порт, отсутствующий production URL или неверная схема URL останавливают запуск с кодом 1. Если недоступна БД или подготовка схемы не прошла, приложение выдаёт общее сообщение и завершается до открытия порта.
- Публичный `GET /health` выполняет `SELECT 1` через используемое приложением подключение без проверки сессии. При успехе возвращает HTTP 200 и `{"status":"ok"}`. При ошибке БД или превышении трёхсекундного тайм-аута PostgreSQL возвращает HTTP 503 и `{"status":"unavailable"}`. Оба ответа содержат `Cache-Control: no-store`. Чекер Exercise 4 проверяет HTTP 200 и не требует поля `db`.
- Без настроек Google маршрут входа Google возвращает 503 с подсказкой использовать пароль. Ошибка Gemini оставляет форму доступной для ручного ввода.
- How I checked — отдельные запуски `node src/server.mjs` проверили отсутствующий и пустой production URL, `PORT=3e3`, URL с неверной схемой и ошибку открытия SQLite. Во всех случаях был код 1 и ожидаемая диагностика без строки URL. Вызов HTTP-обработчика с подставным пулом подтвердил 200 → 503 → 200 при отказе и восстановлении БД, один запрос к БД на проверку и отсутствие установки cookie. Отдельный тест подтвердил ошибку на закрытой SQLite и тайм-аут зависшего запроса к подставному пулу PostgreSQL.

## MCP в production

`npm run mcp` запускает отдельный сервер stdio для доверенного локального клиента. Render публикует только HTTP-приложение. Для проектных инструментов процесс использует действующий user token через `MCP_SESSION_TOKEN` и ищет пользователя по сессии в общей БД. Проектные операции выполняются от имени этого пользователя, вызывают те же сервисы, что и HTTP, и соблюдают ограничения владельца регистрации и ёмкости события.

How I checked — сопоставил код `mcp-server/server.js` и `test/mcp-project.test.mjs`. Файл тестов MCP прошёл в локальном запуске. Проверка `node mcp-server/check.mjs -- npm run --silent mcp` дала 2/8, шесть проверок завершились по тайм-ауту ожидания ответов дочернего процесса. При прямой подаче JSON-RPC из временного файла сервер ответил на `initialize` и `tools/list`. Повторите штатный чекер в Codespaces. **Ожидается** проверка с учебной production БД и сессией, переданной через защищённое окружение локального клиента. Проверьте `upcoming_events`, собственные `my_registrations` и `register_for_event` для тестового события.

## Known gaps — по риску

1. **Высокий — безопасность на Render.** Проверить HTTP → HTTPS, флаги сессионной cookie, заголовки и Console, защиту страниц и API без сессии, недействительность сессии после выхода и недоступность создания события обычному участнику. Проверить, что журналы деплоя не раскрывают чувствительные значения.
2. **Высокий — отказ и восстановление.** В отдельном стенде Render/PostgreSQL смоделировать недоступность базы при старте и во время работы. Проверить отказ запуска, затем для работающего процесса подтвердить `/health` 200 → 503 → 200 и восстановление чтения списка после возврата БД. Блокировка деплоя при красном CI уже подтверждена запуском #7.
3. **Средний — Google OAuth.** Подтвердить вход, привязку к тому же id и обработку отказа в согласии на Render.
4. **Средний — Gemini.** Реальный вызов из Render проверять в согласованной конфигурации с синтетической афишей. Зафиксировать действующий идентификатор модели, время ответа и расчёт стоимости по тарифу на дату проверки.
5. **Средний — MCP.** Повторить штатный stdio-чекер в поддерживаемой среде и проверить проектные инструменты с авторизованной тестовой сессией на общей БД. Проверить отказ без сессии и отказ записи на полностью занятое тестовое событие (AC-8).
6. **Средний — UI и waterfall.** Проверить шесть открытых пунктов [чеклиста](docs/UI.md#оставшиеся-ручные-проверки) в браузере. После развёртывания сравнить первый и повторный заходы на Render и подтвердить 200 для `favicon.ico`.
